## Контракты, которые фиксируются до UI

### MATCH: допуск, ранжирование, объяснение

`SearchInput` из SRC-A §17.3 — один нормализованный источник для S03/count/search. Не задано = null/any, не false/0. Budget — integer 0…100000, query ≤80; enum и FK валидируются. Unicode NFKC/trim/collapse spaces/lowercase; русское ё/е только индексная копия; казахские разные буквы не объединяются. OR внутри categories, AND между независимыми hard-группами.

| Измерение | Правило |
|---|---|
| Категория | Явно выбрана — hard; тема без категории — soft по focusTags. Если категория и тема заданы вместе, единственный вес 30 относится к теме, hard-категория остаётся отдельным отсевом; тема не назначает диагноз |
| Возраст | При выборе всегда hard. Группы в месяцах с включёнными границами: [0,35], [36,71], [72,119], [120,179], [180,215]. Полное включение → pass; непересечение → fail; частичное/неизвестное → unknown. Для открытого/одностороннего null не доказывать включение |
| Язык/формат | Конкретный выбор по умолчанию hard, переключение в soft только пользователем. Null/пустой языковой список → unknown, не pass. UI locale на эти условия не влияет |
| Бюджет hard | Свежая exact/free ≤B → pass; свежая exact>B или from>B → fail; from≤B, unknown, stale → unknown. Exact/free=0 допустимо как бесплатное только при priceKind=free. Строгость бюджета по умолчанию off |
| Бюджет soft | Свежая exact/free ≤B →1; B<exact≤1.25B →0.5; выше →0; from/unknown/stale →0. При B=0 без деления: только free=0 получает 1 |
| Район | Default soft; hard поддерживается контрактом. Применимость только по ADR-0005. Online N/A не называется отсутствующими сведениями |
| Availability | Только soft предпочтение: accepting=true с актуальностью ≤7 дней. False — известное отсутствие готовности к обращению, не неизвестное; слоты не выводятся |
| Публикация | Скрытый/отозванный специалист или offer исключается независимо от остальных полей и прямой ссылки |

Любой fail исключает услугу из eligible и incomplete. Unknown по hard без fail — только отдельный список после явного действия пользователя, без переименования в точное совпадение. Group by specialist выполняется после оценки услуг; карточка содержит выбранный offerId и все matchingOfferIds. Один специалист может иметь другие incomplete offers, но не дублируется как второй подтверждённый специалист.

Веса SRC-A §9: need/category30 + age15 + language15 + format10 + budget15 + district10 + availability5 =100. A определяется заданными применимыми параметрами запроса, одинаково для всех кандидатов. Пропуск исключает вес; неизвестное у услуги оставляет вес и даёт m=0. `score=100*Σ(w*m)/Σw`; coverage учитывает известные актуальные данные, для неопределённого конечного бюджета from — 0 по ADR-0008. При A пустом оба null, общий каталог по стабильным ID.

Default comparator: score desc → coverage desc → specialistId asc → offerId asc; лучший offer и карточка специалиста выбираются одним comparator. Постоянные hard-факторы могут давать одинаковые баллы, это не медицинская статистика. Цена/район — явно выбранные альтернативные сортировки, без скрытой перестановки UI. Reason хранит code/field/expected/actual/evidenceKind/checkedAt/rulesVersion/localeKey; нельзя подтверждать его данными другой услуги. Укороченный JSON §17.10 не заменяет полный контракт.

Актуальность: цена/контакт 30 дней, availability 7, пересмотр документов 365 — предложения для synthetic P0, не утверждённая политика фонда. Для проверок граница включена: `0 ≤ catalogNow - confirmedAt ≤ TTL`; нет/невалидная/будущая дата — unknown, updatedAt не заменяет проверку. Для возраста/языка/формата отдельный TTL ТЗ не задан: не изобретать такой срок; отсутствие значения или происхождения не считать подтверждённым фактом.

### FLOW: услуга, сравнение, восстановление

Canonical selection — `{specialistId, offerId}` с проверкой принадлежности. На карточке → профиль → compare → S08 сохраняется та же пара. Если профиль открыт без offer, выбрать первый опубликованный по стабильному ID, явно обозначить услугу; без контекста нет текста о персональном совпадении. Неверный ID/несовпадающая пара не подменяется молча другой услугой.

Compare максимум 3 пары, один specialist один раз. Другая offer того же специалиста — явное обновление существующей пары. Изменение фильтров сохраняет список и пересчитывает причины/предупреждения; переход к демозапросу несовместимой offer требует явного просмотра предупреждения. Все CTA S06/S07/S08 используют одну проверку, не только путь из compare. Исчезнувшая/hidden offer блокирует submit, не заменяется «ближайшей».

Состояние S05 — draft, копия applied при открытии; Cancel/Escape не применяют, Reset меняет draft, Apply заменяет applied атомарно. PreviewCount и окончательная выдача считают тем же SearchService.

| Событие | Обещанное восстановление |
|---|---|
| Back/Forward, профиль → выдача, язык в текущей вкладке | Intake/applied/compare/offer сохраняются; при возврате в список восстанавливается scroll. Поиск не живёт в URL с детским контекстом |
| Reload ≤2 часов | Валидный synthetic session snapshot восстанавливает доменное состояние; ID сверяются с catalogVersion и публикацией. Панель фильтров закрыта, незавершённый draft отброшен, acknowledge=false |
| Expired/битый JSON/schema mismatch | Snapshot удаляется только в пространстве приложения, показывается объяснение сброса; не угадывать старую схему. Locale и отдельно сохранённые requests сохраняются |
| Новая вкладка/другое устройство | Нет обещания переноса поиска и compare; locale — в том же browser profile, request — только в том же origin/profile IndexedDB |
| sessionStorage недоступен | В памяти работает; явно сообщить, что поиск не переживёт reload. Если неизвестен pending key, не предлагать слепой повтор как гарантированно недублирующий |
| «Начать заново» | Подтверждение → очистить маршрут/applied/query/compare/selected offer/pending UI, сохранить locale и историю requests; уже выполненная транзакция не отменяется reset |
| «Очистить демозапросы» | Отдельное подтверждение; удалить только app-owned requests и ссылку на pending attempt, не весь browser storage |

### REQUEST: честный локальный автомат

UI: `draft → submitting → recorded_demo`; определённый abort → `error`; неопределённый исход → `checking → recorded_demo | retryable_error`. `recorded_demo → cancelled_demo` только после успешного commit отмены. В хранилище только два конечных статуса, не `submitting/error`. §7.8 idle/recorded — краткие UI-обозначения; реализация использует полный автомат §12.1.

Первое submit после acknowledge создаёт key попытки, закреплённый за offer/specialist/catalogVersion; повтор/timeout использует тот же key. Минимальный pending intent в session snapshot сохраняется до записи; изменение offer создаёт новую попытку только после разрешения прежнего исхода. IndexedDB `requests`, keyPath id, unique idempotencyKey; duplicate → getByKey, не новый ключ. Успех определяется завершением транзакции, а не событием add-request success. После reload сначала readByKey; неизвестный результат чтения не означает отсутствие записи и не разрешает новый key.

Запись: id/key/offerId/specialistId/status/runtime createdAt/updatedAt/catalogVersion/nonPersonalOfferSnapshot с RU/KK названием, ценой/KZT/единицей/длительностью/языками/форматом и датой цены. Не хранить intake, имя, телефон, тему, возраст, query, пользовательский бюджет, текст обращения. Snapshot служит истории заявки; актуальность перед новой попыткой сверяется с каталогом. Уже сохранённую историю нельзя превращать обратно в опубликованную offer.

При отказе IndexedDB нет сообщения об устойчивом сохранении; память допустима для навигации, но не как успешная демозаявка. При сбое отмены прежний статус остаётся, показывается ошибка. Неизвестный ID и ошибка чтения — разные состояния. TTL: удалять requests старше 7 дней по runtime createdAt при старте; cancelled terminal, новое осознанное действие — новая заявка. Подтверждение: «Демозапрос сохранён на этом устройстве. Специалисту ничего не отправлено. Реальная запись не создана» на обоих языках.
