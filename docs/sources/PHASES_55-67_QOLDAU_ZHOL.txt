Незакрытый privacy/legal gate блокирует ввод соответствующих реальных данных, а не разработку тестовой логики.

Переиспользуй выбранную инфраструктуру. При её отсутствии сравни минимальные варианты по размещению, доступу, backup, стоимости и навыкам, прими одно базовое решение. Не оставляй несколько несовместимых архитектур.
Production keys не отправляются клиенту. Авторизация основывается на доверенном session/identity, не на ownerId или role из payload.

9. ФАЗА 58: РЕАЛЬНАЯ ГРАНИЦА ПРОВЕРКИ
==================================================

Очередь модерации имеет ответственного и отдельные scopes: identity, education, contact, offer_data и другие действительно нужные.
Решение содержит scope, status, evidence reference, source, checkedAt, reviewDueAt, проверяющую роль, ограничение и при необходимости причину для владельца.
Public summary отделён от приватного evidence и внутренней причины отказа.
Скан просмотрен ≠ подлинность подтверждена у выдавшего источника ≠ подтверждена эффективность занятий.

Проверка может устареть, быть отозвана или требовать повторного рассмотрения. Публичный бейдж пересчитывается из фактов, а не просто копируется навсегда.
Жалоба — сигнал на рассмотрение, не доказанное нарушение. Защити заявителя и минимизируй сведения ребёнка.
Срок ответа является согласованной целью при наличии исполнителя, не вымышленным обещанием.

Журнал: кто, что, когда, какая версия и основание; без ненужных копий документов и медицинского текста. Audit не должен стать вторым бесконтрольным хранилищем PII.

10. ФАЗА 59: КОНТАКТ И НАДЁЖНОСТЬ
==================================================

Выбери реализованный режим по фактическому процессу:
LIVE_EXTERNAL — разрешённый внешний канал;
LIVE_REQUEST — защищённый серверный приём заявки;
PILOT_TEST — синтетический server/sandbox сценарий.

Перед передачей:
получатель;
услуга и условия;
цель;
точный состав данных;
необходимое подтверждение;
возможность исправить и отказаться.
Не передавай весь intake, дневник и календарь автоматически.

Внешний переход подтверждает только открытие канала, не доставку.
Server commit подтверждает сохранение системой, не получение человеком.
Provider accepted, delivered, responded и appointment_confirmed имеют разные доказательства.
При отсутствии delivery receipt статус delivered не выдумывается.

Идемпотентность:
key scoped к доверенному владельцу и операции;
same key + same canonical payload → прежний ID;
same key + different payload → conflict;
уникальность и атомарность на доверенной стороне;
timeout → сначала проверить тот же key;
не создавать новый key при автоматическом retry.

Если сохранение и внешняя отправка разделены, выбери минимальную устойчивую outbox/job модель или обоснованный эквивалент. Потеря процесса после commit не должна терять работу молча. Не обещай exactly-once доставку у неподдерживающего её провайдера; документируй семантику повторов и дедупликацию.
Обработай provider failure, retry/backoff/предел, неопределённую доставку, отмену и поздний callback.
Callback/webhook проверяется по фактическому механизму подписи/доверия, события дедуплицируются. Не принимай произвольный client payload «delivered=true».

Anti-abuse соразмерна: rate limits, ограничения payload, проверка владельца, защита от автоматических массовых отправок без избыточного fingerprint.
Проверки идут в sandbox/тестовые адреса. Реальные сообщения — только по явному поручению. Не «проверяй доставку» отправкой случайному специалисту.
Backend failure не переключает live на локальное «отправлено».

11. ФАЗА 60: ТРЕКЕР И ПОДТВЕРЖДЕНИЯ
==================================================

Раздели:

доставку при доказательстве;

ответ;
ручное сообщение родителя о договорённости;

отмену/закрытие.

Событие содержит actor, source, timestamp, version, разрешённый payload. История не редактируется клиентом произвольно.

После доставки нельзя обещать отозвать внешнее сообщение.

12. ФАЗА 61: КАЛЕНДАРЬ

source manual|confirmed_request|other_supported;
requestId/offerId при наличии;
public place reference или минимальный адрес;
status planned|confirmed|cancelled по договорённому контракту;
version;

необязательная минимальная заметка.

Date-only и события с временем различаются; не превращай календарную дату в UTC-полночь без смысла.

Связь confirmed request → event идемпотентна по стабильному источнику. Повтор webhook не создаёт вторую встречу.
Редактирование использует version; конфликт не затирает новое событие молча.
Отмена меняет статус и связанные reminder jobs; источник изменений сохранён.

Повторяющиеся события вводи только в нужном объёме. Если реализованы, заранее определи series/occurrence, исключения и «одно/последующие/вся серия». Не добавляй recurrence, если достаточно одиночных событий текущего пилота.
Внешние Google/Apple календари и OAuth не подключаются автоматически. Экспорт, если отдельно выбран, показывает, что выгруженный файл может содержать приватный адрес/заметки и не отзывается после скачивания.

Проверь переход месяца/года, високосную дату, выбранную временную зону, изменение времени и при заявленной поддержке зон — соответствующие переходы времени.

13. ФАЗА 62: НАПОМИНАНИЯ И РЕАЛЬНАЯ ПОДДЕРЖКА
==================================================

Сначала выбери один канал с существующим провайдером/инфраструктурой. Проверь актуальные официальные документы и реальную поддержку устройств.
PWA-установка сама по себе не гарантирует произвольные фоновые локальные напоминания на всех платформах. setTimeout в открытой вкладке не считается устойчивым scheduler.
Если надёжный канал недоступен, реализуй честную in-app подготовку/тестовый адаптер и отдельно отметь внешний delivery blocker. Не подменяй это обещанием push при закрытом приложении.

Пользователь выбирает событие, канал и смещение. Разрешения запрашиваются после понятного действия, не на первом экране.
Отказ не ломает календарь. Есть выключение и корректировка.
Для lock screen по умолчанию нейтральный текст без диагноза, имени ребёнка и подробностей занятия.

ReminderJob связывает eventId, eventVersion/occurrenceId, owner, channel, fireAt, lifecycle, попытки и безопасный provider reference.
Изменение события инвалидирует прежние jobs и создаёт согласованные новые. Перед фактической отправкой перепроверяй актуальную версию, отмену, подписку и доступ.
Отмена и повтор дедуплицируются. Scheduler устойчив к перезапуску по выбранной архитектуре; не нужны микросервисы ради одного job.

Разделяй scheduled, processing, accepted_by_provider, delivered при receipt, failed, cancelled, unknown_delivery.
Retry со сроком и пределом; просроченное напоминание не отправляется бесконечно через несколько дней без согласованного правила.
В гонке отмены и уже начатой внешней отправки честно покажи ограничения: отправленное нельзя гарантированно отозвать.
Проверь двойное выполнение job, конкурентные workers при применимости, callback replay и provider timeout.
Тестовые доставки не идут реальным семьям без поручения.

14. ФАЗА 63: ПОДПИСКИ НА ИЗМЕНЕНИЯ
==================================================

Подписка opt-in, имеет владельца, конкретную offer, выбранные виды изменений, канал и отключение.
Значимые поля: цена/вид/единица, адрес/координаты, формат, язык, публикация, актуальная готовность принимать обращения и существенные факты доверия по согласованной модели.
Обычный updatedAt и косметическая правка не порождают «условия изменились».
Diff строится по версиям и нормализованным значениям. Старое и новое относятся к одной offer, даты и источники видны.
Change event имеет стабильный ID; дедупликация subscription/event не допускает повторный спам. При необходимости объединяй несколько последовательных правок в понятное сообщение.
После unsubscribe новые jobs не создаются; pending jobs проверяют актуальное состояние перед отправкой.

Уведомление скрывает лишний семейный контекст. Оно не подтверждает доступные слоты.
Withdrawal не удаляет исторические минимальные факты произвольно и не оставляет активную ссылку на публично скрытый профиль.
Офлайн-копия остаётся копией до получения обновления. Не обещай мгновенное удаление на отключённом устройстве.

18. ФАЗА 67: РЕЗЮМЕ К ВСТРЕЧЕ И ПЕРЕДАЧЕ
==================================================

По умолчанию ничего приватного не выбрано. Родитель явно отмечает вопросы, цели, наблюдения, даты и организационные сведения.
Покажи полный draft и получателя перед внешней передачей. Источники и авторство записей не должны превращаться в клиническое заключение приложения.
Вывод содержит ровно выбранное, без скрытых полей, полного дневника и приватных metadata.

Минимальные варианты:
просмотр;
редактирование собственного draft;
копирование;
скачивание выбранного формата при необходимости.
Success clipboard/download основан на фактическом результате, есть доступный fallback.

Отправка отдельна и не выполняется от открытия preview. Если канал не реализован, не показывай «доставлено».
Для защищённой ссылки нужны ownership, получатель/scope, срок, механизм доступа и отзыв. Не создавай публичную URL с приватными данными в query и не полагайся на угадываемость UUID.
Если безопасная link-sharing модель не входит в текущий выбранный объём, оставь просмотр/копирование/скачивание с явным ограничением, а защищённую отправку пометь как не реализованную.
Отзыв ссылки не возвращает скачанный файл или скопированный текст. Удаление исходной записи не гарантирует удаление внешней копии.

При переходе к другому специалисту не открывай старому доступ к новому взаимодействию или всему семейному контексту автоматически. Передача только выбранных сведений не подразумевает совместный доступ семейной фазы 68.

==================================================
19. BACKEND, КОНКУРЕНТНОСТЬ И МИГРАЦИИ
==================================================

Одна минимальная поддерживаемая серверная архитектура по проекту, без брокеров и микросервисов по привычке. Durable jobs/outbox реализуются существующими средствами при достаточной надёжности.
Выбери один канонический путь записи каждой операции. Не дублируй несогласованно прямой клиентский доступ и привилегированный endpoint.
Проверяй типы/размеры/enum/ownership до побочного эффекта. Не доверяй display label роли и клиентским полям проверки.
Публичные и приватные DTO разделены. Internal evidence, consent content и diary не просачиваются через вложенные relations/экспорт.

Миграции версионируются, проверяются на тестовых данных, имеют preservation/rollback plan по смыслу изменения. Не применяй их к неизвестной production-БД и не удаляй данные ради «чистой схемы».
Уникальные ключи защищают idempotency, источники календарных событий, jobs и subscriptions по контракту. Constraints не заменяют авторизацию.
Optimistic locking/транзакции предотвращают silent overwrite.
Используй Clock для расписаний/проверок и реальную доверенную дату записи по назначению; demoClock не превращается в timestamps настоящего обращения.
Логи безопасны: коды, технические ID и корреляция без свободных медицинских текстов и секретов. Сроки логов и audit отдельны.

==================================================
20. ПРИВАТНОСТЬ, ОФЛАЙН И PWA
==================================================

Приватные дневник, задания, контакты и календарные заметки не попадают в прежний публичный Cache Storage.
Service worker не кэширует приватный API как app shell и не возвращает HTML вместо успешного JSON.
Синтетические saved cards и реальные персональные записи имеют разные политики/namespace/modes. Нельзя незаметно превратить старое demo-хранилище в live-family storage.
На общем устройстве пользователю понятны вход/выход/очистка. Logout и отзыв доступа должны обработать собственные приватные кэши в согласованной модели, не удаляя чужие данные origin.
Локальное шифрование не объявляется реализованным без модели ключей, угроз и проверок. IndexedDB не становится автоматически безопасным медицинским сейфом.

Если офлайн-редактирование приватного дневника не входит в объём, покажи read-only/not available, не имитируй вечную синхронизацию.
Если оно действительно необходимо, до реализации нужны pending operations, ownership, конфликт версий, reconnect, access revocation и deletion policy. Не добавляй сложную синхронизацию молча.
Offline change не называется серверно сохранённым. Удалённый доступ нельзя гарантированно отозвать на отключённой ранее скачанной копии; ограничение отражено.
Уведомления не содержат чувствительных деталей по умолчанию.

==================================================
21. ЛОКАЛИЗАЦИЯ И ДОСТУПНОСТЬ
==================================================

Все новые системные интерфейсы RU/KK: onboarding, moderation, request/tracker, calendar, reminders, subscriptions, next step, diary, задания, summary, ошибки, подтверждения и доступные названия.
Смена locale не меняет время события, owner, status, recipient и выбранные записи. User-authored text не переводится внешним API автоматически.
Непроверенная редактура носителем помечена. Date/number/currency форматируются при отображении, не являются форматом хранения.

Мобильные 360/390/430, reflow320 CSS px, desktop, zoom, длинные KK-строки, focus, keyboard, screen-reader smoke и reduced motion.
Calendar имеет доступный список/agenda, а не только drag-and-drop сетку.
Напоминания можно отключить без жестов; status не только цвет.
Goal/diary/task формы имеют labels, пределы, безопасные ошибки и сохранение введённого при неудаче в разрешённых пределах.
Поддержка Қарлығаш уважительна, без обещаний лечения, давления и сравнений детей.

22. ТЕСТОВЫЕ АКТОРЫ И РЕСУРСЫ
==================================================

Создай синтетические actors:
PARENT_A и PARENT_B;
SPECIALIST_A и SPECIALIST_B;
MODERATOR;
ADMIN при необходимости;
GUEST.
Каждый имеет отдельные resources и явные разрешённые связи. Идентичности тестов не являются действующими production-учётками.

Обязательные отрицательные случаи:
A читает/меняет запрос B;
A открывает дневник B;
специалист A назначает задание чужому контексту;
специалист B видит задания A без разрешения;
специалист меняет verification;
parent подставляет role/ownerId;
guest получает evidence/diary;
moderator получает весь дневник без основания;
прямой API обходит скрытый UI;
отозванное разрешение используется старой сессией;
экспорт включает скрытые записи;
ссылка раскрывает приватный текст;
demo key/режим активирует live;
неподтверждённый callback меняет delivered/confirmed.

Результат denied не должен содержать чужие данные. Выбери согласованную not-found/forbidden политику без лишнего раскрытия существования приватного ресурса.

23. СКВОЗНЫЕ СЦЕНАРИИ И ПРОВЕРКИ
==================================================

T1. Existing CORE/PWA
A/B/C, ru/kk, selected offer, compare, local demo create/reload/cancel, offline saved card, reset и карта после изменений.

T2. Specialist lifecycle
draft → submit → запрос изменений → повтор → разрешённая публикация → изменение цены → пересмотр/withdraw. Public/private проекции проверены.

T3. Moderation
role checks, scopes, stale/revoked, evidence, отсутствие self-verification, безопасный журнал.

T4. Contact/tracker
согласованный получатель/payload → server commit → sandbox processing → receipt по поддержке → ответ/ручная договорённость → отмена.
Проверь double click, same key same/different payload, timeout, restart, callback replay, поздний ответ, provider failure, чужой ID.

T5. Calendar
manual и confirmed различаются; request retry не дублирует event; edit conflict; отмена; месяц/год/зона; отсутствие приватных данных в публичном URL.

T6. Reminders
opt-in, denied permission, schedule, event edit/cancel, job dedup, stale revision, retry, provider accepted без delivered, отключение, гонка отмены/отправки.

T7. Offer changes
существенный diff, косметический no-op, same change event, unsubscribe, withdrawn, private-safe text, offline snapshot не обновлён до sync.

T8. Next action
реальный источник, ручная отметка, defer/hide, отсутствие дублей и изменения appointment без факта.

T9. Goals/diary
создать/изменить/удалить, version conflict, ownership, размеры/опасный HTML, нет публичного индексирования, backup limitation и audit metadata.

T10. Assignment
уполномоченный автор, разрешённый recipient, version/revision, response, unable/question, withdraw, запрет чужого доступа, отсутствие медицинского auto-score.

T11. Summary
default private selection empty, точный выбранный состав, preview, редактирование draft, copy/download failures, нет автопередачи, отсутствие лишнего diary, link permissions/revoke только при реализации.

T12. UI
RU/KK, keyboard, accessible calendar agenda, mobile, длинные строки, network/server/storage failures, focus, повтор операции без потери статуса.

Unit/integration/e2e/manual имеют собственные цели. Mocks не заменяют проверку реальной серверной авторизации и хотя бы согласованного sandbox-пути, если эти компоненты заявлены реализованными.
Попробуй выполнить доступные браузерные проверки; конкретный блокер отметь. Непроведённый тест родителя не выдумывай.
Не отправляй настоящим пользователям тестовые напоминания и задания.

25. GO/NO-GO И ОТСЕЧЕНИЕ ОБЪЁМА
==================================================

Оцени отдельно:
CORE/PWA;
PILOT_TEST backend;
onboarding/moderation;
contact/tracker;
calendar/reminders;
change subscriptions;
next action;
diary/tasks;
summary;
PILOT_LIVE.

Blocker:
чужие приватные данные доступны;
role/owner spoofing;
ложная доставка/встреча;
реальные сообщения из test;
дубли логической операции;
утечка секретов;
public caching diary;
медицинский auto-score;
повреждение данных;
отсутствие существенных live-оснований при попытке реального запуска.

Major:
потеря введённого/подтверждённого статуса без объяснения;
неверные dates/timezone;
отмена не инвалидирует pending reminder;
неверный recipient;
нечитаемый основной RU/KK путь;
заявленный внешний процесс фактически отсутствует.

Непроверенный/недоступный модуль выключается честно, не фальшивой кнопкой. Это не разрешение назвать все 55–67 готовыми.
READY: порученный согласованный объём работает и проверен, внешние условия закрыты для заявленного режима.
READY WITH LIMITATIONS: конкретные ограничения не скрыты; указано, что разрешено только в test/demo.
BLOCKED: существенный контракт/ресурс мешает заявленному результату.

Если времени мало, сначала уменьши число каналов, повторяемые события, декор и дополнительные виды exports. Не сокращай ownership, достоверность статусов и существенные проверки ради видимости полноты.
